## 结论与估算口径

可行，属于跨子系统的中大型重构。当前加载器可复用，但完整天境不能直接由现有 SDK 表达。
估算以一名熟悉本项目的 C++ 开发者、每人日约 8 小时、功能与生成结果保持一致为前提。
数字是基于源码依赖的规划区间，未做迁移原型或性能基准，不是交付承诺。
包含实现、相关测试扩充及可用平台的本地验证；取得其他平台设备和 CI 反馈的等待时间另计。

| 方案 | 范围 | 估算 |
|---|---|---|
| 插件开关包装 | 由官方插件启停现有天境；专用定义、生成和行为仍在宿主 | 3–6 人日；只适合作为过渡 |
| 官方天境完整内容插件（建议） | 注册控制维度可用性；迁出内容、生成、结构、交互和表现；宿主提供通用能力，可保留历史维度槽位和 ID 保留项 | 25–40 人日，约 5–8 工作周 |
| 通用第三方维度体系 | 进一步允许任意维度数量、命名空间维度标识和独立桌面插件；存档、LAN、UI 均取消固定双维度假设 | 40–60 人日，约 8–12 工作周 |

后三方方案的 40–60 人日是总量，不是在官方插件工期上再加该数。
后两方案均假设新世界采用新插件身份；若要求旧世界继续读取和保存，另预留 5–10 人日。
原地跨版本升级、完整备份恢复和大量旧版本组合可能进一步扩大兼容工作。

## 当前实现依据

- `src/plugins/PluginManager.cpp`、`ContentRegistry.h`：启动时加载，注册事务回滚，冻结注册表，
  方块/物品运行时 ID 从 4096 起；已有配置、依赖、世界要求和 LAN 指纹。
- `sdk/minecraftc/plugin.h`：现有 MC_Block 只有立方体或交叉植物描述，没有阶梯、门、按钮状态族注册。
  有发光和简单掉落，但没有叶片透光/燃烧/燃料/种植支撑等完整材料语义。
- `sdk/minecraftc/extensions.h`、`src/plugins/PluginExtensions.cpp`：生成扩展只接受 dimension 0/1；
  没有注册新维度的接口，也没有批量体素、多层 LOD、结构定位或结构战利品输出接口。
- `src/game/GameRules.h`、`src/app/GameSession.h`：DimensionId 固定为 Overworld/Heaven，
  simulations 与创建生成配置均为长度 2 的数组。
- `src/game/SaveStore.h/.cpp`：专用 heaven 状态、两个生成配置、固定维度值检查；
  `GameSession::ensureDimension` 使用 `dimensions/heaven` 路径。
- `src/network/PlayerProfile.h` 及各 Protocol：双维度位置和编号校验；通用维度方案须共同升级协议。
- `src/world/WorldGenerator.h/.cpp`：天境 v9，5 个岛层、8 个群系，出生点、生态、跨层交通及结构查询。
  Heaven 专用 populate 函数从第 908 行开始，到生成编排前，约 500 行；周边采样逻辑也须迁出。
- `src/world/LodTerrainSystem.cpp`：浮岛上下界、多层 span、细节采样与特殊装饰处理均有天境专用逻辑。
- `src/world/StructureGenerator.cpp`、`WorldPersistence.cpp`：4 类天境结构和战利品，含起源神殿保证权杖。
- `src/player/Player.cpp`、`GameSession.cpp` 及 LAN 睡眠路径：床入口、掉入虚空返回、死亡返回，
  星步权杖目标检查、传送、冷却和耐久；当前 SDK 没有直接玩家传送/换维度操作。
- `src/renderer/RenderEnvironment.h`、`ParticleSystem.cpp`、`HeldToolModel.cpp`、Vulkan 与 sky.frag：
  天空、粒子、权杖模型和预览有专用路径；环境回调只覆盖部分颜色与光强。
- `src/platform/sdl/SdlAudioSystem.cpp`：天境双曲播放列表写在音频适配器中；SDK 尚无播放列表注册。
  `assets/lang/`、纹理定义/生成工具、资源安装也需审查和迁移。

按维度名扫描，src 内有 40 个 C++ 源/头文件含 Heaven/heaven/HEAVEN 引用；
内容名称另涉及 Block.cpp、SurvivalRules.cpp、WorldPersistence.cpp 等文件。
这是依赖扫描范围，不是承诺的实际改动文件数。

内容规模：10 个早期方块 + 16 个 v9 方块 + 日石/云石 20 个阶梯/台阶状态 +
天空木门 64 状态 + 天空木按钮 24 状态，共 134 个序列化方块状态；
对应约 38 个物品条目（含权杖、资源、食物、门和按钮）。不能仅按 26 个基础方块计算。

## 技术决策与主要风险

1. **先采用官方内置插件。** 建议命名 `official_heaven`，默认启用，可禁用，加载时注册；
   Android/iOS 继续编译内置代码，桌面以后可复用相同接口生成动态库。
   内置插件仍随应用编译，是否加载与玩法是否存在由注册决定。
   目前内置示例的默认开关和入口选择只覆盖两个插件，须改为通用内置描述表。
   内置包的资源根、Title Storage 与外部 mods 资源路径也需要统一。
2. **保留历史数字，不保留无条件内容。** 不移位已有 BlockId/ItemId；旧编号可作兼容保留项。
   真正的插件运行时定义使用命名空间键。官方插件方案可保留维度槽位 1，
   但启用性、生成与规则由提供者注册决定；任意第三方维度需要另外泛化容器和协议。
3. **存档门禁必须设计。** SaveStore 每个持久化文件均检查精确玩法插件集合；
   默认启用新插件会令此前无插件世界不匹配，未到过天境也一样。
   当前调色板只重映射 ID≥4096 的插件内容，旧天境低编号不会自动转成新键。
   完整兼容需覆盖 level、区块覆盖、方块实体库存、掉落实体、玩家与 LAN 访客背包、
   维度路径和生成选择；不能只修改 level.bin 的插件要求。
   建议提供明确版本条件的读取映射/受控升级，备份并验证后保存；禁止静默替换或降低门禁。
   禁用天境插件时应拒绝加载依赖它的世界，并且不写入存档。
4. **逐体素回调不能视为性能等价。** 当前 generatePluginChunk 每块 16×384×16，
   有 98,304 次体素采样；LOD 自定义生成器也逐列扫描 384 层。
   天境复杂层、生态和结构若每次重复计算会放大代价。应补齐批量生成和稀疏多层 LOD 接口，
   缓存必须只依赖 seed/坐标/不可变参数，且插件卸载前等所有 worker 完成。
5. **结构不能只输出方块。** 现有 modifier 输出只有位置和 BlockId，不能表达宝箱 loot profile/seed。
   要保留起源权杖、结构定位、跨区块覆盖顺序，必须扩展元数据和宿主持久化接口。
6. **形状和能力通用化。** 通用门/按钮/台阶实现应继续由宿主拥有，插件注册材料和状态族，
   避免天境复制碰撞、电力和网络逻辑；叶片、藤蔓、矿石掉落、燃料也使用通用属性。
7. **表现需要更完整的输入。** MC_Environment 不暴露完整日夜相位、天体方向和 skyStyle；
   render stage 可替换天空，但粒子/云/音频仍另有宿主管理，不能认为已有 render 扩展能完整搬走表现。
   新接口保持 Vulkan/SDL 适配器边界，GPU 资源仍在主/渲染线程管理。
8. **生成版本按结果决定。** 抽取算法若保持种子到输出映射，可保留天境 v9 和全局 v20，
   通过插件生成器 revision/fingerprint 区分缓存。若输出变化，必须明确版本决策，更新确定性测试；
   不以移动代码为理由掩盖新旧区块接缝。存档/网络结构改变则另外评估格式与协议版本。

## 实施顺序与验收

先固定 v9 输出和玩法回归基准，再添加通用维度提供者/状态族/批量生成接口，
逐包迁出内容与生成、LOD、结构交互、表现；最后核验宿主没有天境专用玩法分支。
若选择旧存档兼容，兼容设计在第一阶段确定，升级验证在集成阶段完成。

关键验收：关闭插件后新世界没有天境入口、内容和配方；依赖世界显示清楚拒载原因且零写入；
启用后同种子输出、负坐标、region/singleton、跨边界结构与 v9 基线一致；
叶片/灯/藤蔓、门/按钮/台阶、宝箱权杖、跨层交通与虚空返回保持行为；
多层 LOD 加载和生成耗时与基线比较；LAN 缺包/版本不符拒绝，匹配时所有交互由宿主授权。
按阶段运行受影响构建、完整 CTest、API 边界检查和 Vulkan smoke，最终覆盖五平台构建/包装。
